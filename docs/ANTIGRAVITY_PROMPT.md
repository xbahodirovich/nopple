# Antigravity handoff prompt

Continue implementing Mopple in this repository. Finish the home-design workflow described below; ship working code, not a mockup or another plan. Preserve the existing dark/mint studio, landing page, logo assets, shared project engine, undo/redo, import/export, offline editing, accessibility and mobile behavior. Read PRODUCT.md, README.md, docs/editor-system.md and docs/mopple-format.md first. Respect applicable AGENTS.md instructions. Do not modify design.md or restore a map.

## User's intended experience

When a user asks AI to design a house, AI first learns everything the user wants. It asks relevant follow-up questions, summarizes all requirements and obtains approval BEFORE generating architecture or a model. After approval, create a coherent architectural design, a detailed realistic 3D house, and photorealistic images of the future interiors. All outputs must represent the same approved house and honor the complete brief, including shadows, sunlight, material highlights, reflections and artificial lighting. Users can freely change sun direction and height. There is no map UI or map ground overlay.

## Foundation already implemented

- Vite + TypeScript + Three.js + Zod; Node same-origin NVIDIA NIM proxy for existing-design operations. No React or application framework. Personal API keys stay in tab memory. Do not place secrets in VITE variables or .mopple files.
- `src/editor/brief.ts`: accessible native dialog for original request, area, bedrooms, bathrooms, floors, architecture/interior style, site/climate, household/accessibility, other rooms and must-haves, materials/furniture, budget/priorities, lighting, and requested interior images. All answers required; users may explicitly state no preference. Editable review and confirmation precede geometry creation. Cancellation does not modify the project. A revision guard blocks replacing a project changed while reviewing.
- House creation prompts open the brief. `executeAiPrompt` and the AI operations endpoint reject direct create_house/update_design_brief requests. Existing editing commands still work. The starter deliberately does not call an LLM; it creates a deterministic one-floor concept and saves the full brief in a single undoable transaction.
- `src/project/brief.ts`: validated DesignBrief and explicit starter capability report. `metadata.designBrief` round-trips in .mopple, autosave and undo/redo. Numeric limits currently follow the starter: 40–600 m², 1–8 bedrooms, 1–5 bathrooms, 1–5 requested floors. Floors beyond one are retained but not built. Do not silently discard such requirements.
- `src/project/generation.ts`: downloadable versioned generation-plan JSON, authoritative project snapshot and original brief, stages marked concept_only/not_implemented, provisional per-room interior jobs and realism prompts. Nothing runs those jobs yet. Camera is explicitly null. The Render plan button enables after a brief exists. This is a provider-independent handoff contract, not rendered output.
- `src/editor/solar.ts` / `canvas3d.ts`: manual azimuth 0–360° clockwise from scene north (-Z), height 1–90°, live preview updating directional light and sky. `metadata.sun` + update_sun persist on slider release with undo/redo. Date/solar-time mode remains available; manual mode hides irrelevant solar controls. Map controller and plot texture removed; `site.ts` retains old geographic defaults/presets, and legacy metadata.geo.mapUnderlay remains accepted for import compatibility but is ignored by rendering.
- `canvas3d.ts` fits the house instead of the oversized ground. Existing procedural materials and furniture are still conceptual. Current geometry is not a complete exterior: finish roofs, ceilings, stairs, facades and details as needed.

## What to implement next, in dependency order

### 1. Conversational requirements and durable approval

Replace/extend the static questionnaire with a genuine conversational AI discovery flow. Parse the initial request into structured fields; ask only for missing or conflicting details. Support natural language, multiline requests, corrections and uploaded references. Cover site/buildable footprint, orientation/climate, occupants/accessibility, floors/area, every room and adjacency, indoor/outdoor areas, style, finishes, furnishings, budget/currency, lighting, requested render rooms/viewpoints and any custom constraints. Retain every original answer and explicit “designer's choice.” No silent defaults for important decisions.

Persist drafts and conversation separately from committed geometry, survive reload, and allow users to resume. Present a readable complete brief with editable answers. Track explicit approval of a specific brief version. Revisions invalidate affected downstream artifacts. A generic edit to an existing house must not accidentally start or replace a house. Replace regex-only routing with structured intent detection plus safe server validation.

### 2. Shared generation orchestration and requirement coverage

Add a server-side project generation API and provider adapters. Keep the ordinary operations endpoint focused on edits. Validate the approved brief, current project revision and approval token before starting; do not merely re-enable create_house in the existing endpoint. Use a durable job model with queued/running/succeeded/failed/cancelled/stale states, per-stage progress, bounded retries, cancellation, timeouts and retry without losing successful work. Include idempotency keys, request/brief/project revisions and an artifact manifest.

Generate architecture first, detailed scene second, then conditioned interior renders. Maintain a requirement-to-artifact coverage report: every user requirement is fulfilled, explicitly unresolved, or awaits a user decision. Block misleading “complete” states while requirements remain unfulfilled. Present infeasible combinations or budget conflicts and ask the user to resolve them. Commit validated geometry atomically. Reject stale responses; preserve existing design on errors; keep replacement undoable. Provide preview and approval for materially changed plans.

### 3. Real architecture and detailed 3D

Move beyond the fixed central-hall one-floor layout. Produce constrained layouts matching requested room counts, areas, floor count, circulation, adjacencies, accessibility, plot/setbacks and orientation. Build shared walls and valid non-overlapping openings, doors with clearances, windows, stairs/floor connections, roof, ceilings, facade and exterior amenities. Generate useful dimensioned plans and elevations from the same canonical geometry. Extend the schema with backwards-compatible migrations and tests instead of inserting unrelated scene objects that disappear on export.

Build a coherent detailed 3D scene from that geometry: appropriate furniture at real scale, cabinetry, fixtures, trims, window frames, glass, exterior detail and landscaping where requested. Use properly licensed GLTF/GLB assets and texture sets with documented sources. Support PBR albedo/normal/roughness/metalness maps, realistic glass, reflectance, exposure/tone mapping, environment illumination and contact shadows. Address daylight through glazing and reduce flat procedural look. Add usable exterior, cutaway and room cameras; preserve selection and model editing. Keep performance bounded through caching, disposal, LOD and progressive quality. Gracefully support mobile, reduced motion and WebGL failure.

### 4. Photorealistic interior images that match the project

Implement an actual rendering backend/provider, with configuration and a functioning end-to-end path. Evaluate current official provider documentation before integration. The existing NIM text-model credentials do not imply image generation support. Use separately configured credentials where required; never invent an image endpoint or expose a shared server secret. If credentials are absent, show a clear setup/unavailable state with preserved jobs, not sample images labeled as generated output.

Choose a geometry-grounded renderer or an image pipeline conditioned on scene captures, depth, normals and other appropriate controls. Free-text-only unrelated house photos are unacceptable. Lock room dimensions, window/door placement, furniture layout, materials, camera and light state. Resolve the user's desired rooms and viewpoints against the final model; do not blindly use the provisional per-room jobs. Select physically valid interior camera positions with sensible lens and no wall clipping.

Aim for believable daylight/window light, soft and contact shadows, indirect bounce, artificial sources, specular highlights, polished stone/metal reflections, rough material response, glass transmission and natural exposure. Support daylight, golden hour and artificial evening lighting when requested. Keep sun direction consistent between preview and final renders. Store artifact URLs/files, dimensions, provider/model, prompt, camera, room ID, brief version, scene revision, seed where supported, generation settings and provenance. Add gallery states for queued, rendering, complete, failed and stale outputs with full-resolution download, retry and regenerate controls. Image failure must not discard architecture or 3D.

### 5. Sun study completion

Keep map removal permanent. Preserve direct manual azimuth/elevation controls and persist all additional light settings. Extend sun settings with intensity, warmth, softness and environment if useful. Date/time controls currently use an approximate solar-time calculation with legacy/default coordinates; they are not a timezone-correct location study. If retaining that mode, correct and verify astronomical azimuth convention, timezone/date/DST handling and initialization, expose location as simple fields rather than a map, persist it, and label accuracy honestly. Avoid repeatedly rebuilding heliodon guide geometry on every frame; dispose old geometry/materials/textures. A persisted manual light must drive export and high-quality renders, including on projects without a predefined sun light.

Verify sun direction changes actual pixels/shadows, survives reload/export/import/undo, and matches rendered interiors. Test desktop and mobile, keyboard-only dialog/chat/gallery use, readable progress/errors and no horizontal overflow.

Use a representative request with a two-floor house, multiple bedrooms, office, courtyard, specific materials and accessibility needs. Show the approved brief, matching architecture, matching detailed 3D, and at least one successfully generated, geometry-consistent interior image using a configured provider. If credentials prevent a live call, clearly distinguish mocked contract tests from live verification and document exactly what remains unverified.

Update README and implementation docs to describe shipped behavior and setup. Deliver a concise report of changes, actual verification and remaining limitations. Do not claim construction-ready engineering plans or photorealistic output from the current starter. Do not deploy or publish without authorization.
